**LLM inference** is running a trained model on new input to produce an output. **Serving** a model
means keeping GPU compute running and exposing the model through an API your application can call.
On Emissary, the unit you create is an **inference engine**: Emissary provisions the GPU compute,
loads a base model, and exposes an HTTP API. You then deploy base models and your own fine-tuned
checkpoints onto it, scale it to traffic, and put it on a schedule to control cost.

## How does inference work on Emissary?

Three resources, one on top of the other:

1. **Inference engine.** A managed, GPU-backed serving unit, bound to one base model and one task
   type for its lifetime. You don't choose hardware: Emissary selects the GPU type and number of
   GPUs, and shows an estimated hourly cost before you create the engine. Billing starts when the
   engine reaches the **Active** state and stops when it is deactivated.
2. **Deployment.** A specific model version served on an engine. Every engine exposes a **base
   model deployment**, and you can add **fine-tuned deployments** from your checkpoints. You call
   each deployment by name.
3. **Replicas.** The GPU-backed copies of an engine that handle traffic. On a cluster engine, the
   number of replicas changes with load.

See [Concepts](./concept) for each of these in detail, and [Deployments](./deployments) for creating,
calling and managing them.

## How do I serve many fine-tuned models cheaply?

Fine-tuned deployments for the `text-generation`, `classification` and `regression` task types are
served as **LoRA adapters**: lightweight weights layered on top of the shared base model. The base
model stays resident in GPU memory and only the small adapter weights are swapped in, so many
fine-tuned deployments can coexist on one engine. Each request names the deployment it should use,
which lets you A/B test versions or serve many customers' adapters from one endpoint. Other task
types serve a single model per engine.

## What is the difference between on-demand and cluster engines?

Emissary picks the server type for you, based on whether you enable autoscaling.

| | **On-demand** | **Cluster** |
| --- | --- | --- |
| **Capacity** | Fixed, a single instance | Elastic, multiple replicas |
| **Autoscaling** | No | Yes |
| **Best for** | Development and steady traffic | Production, and bursty or high-throughput traffic |
| **Enabled when** | Autoscaling is off (the default) | Autoscaling is on |

## How does autoscaling work?

Provision for peak load and you pay for idle GPUs whenever traffic is low. Provision for average
load and requests pile up when traffic spikes. **Autoscaling** removes that trade-off: Emissary adds
replicas when load rises and removes them when it falls, so capacity tracks demand. You set:

- **Min and max replicas**, the floor and ceiling.
- **The autoscaling metric:** request rate per replica, or concurrent requests per replica.
- **Upscale and downscale delays**, which control how long sustained load must persist before a
  replica is added or removed.

See [Autoscaling](./autoscaling) for how the decision is made and how to tune it.

## What can I serve?

Supported task types include `text-generation` (chat and completion), `classification`,
`regression`, `embedding`, `ner`, `image-detection`, `vlm-classification`, `vlm-generation`,
`clip-classification` and `clip-embedding`. Which are available depends on the base model you pick.

## How does inference connect to post-training and routing?

- **From post-training.** A checkpoint you trained serves nothing until you deploy it on an engine.
  See [What is post-training?](../fine-tuning/what-is-post-training).
- **From routing.** A router sends a lot of work to open models, and shared endpoints price those
  models for the average workload. Dedicated inference runs them on capacity tuned to your traffic
  shape, with no noisy neighbors and more predictable latency under load. See
  [from routing to your own models](../routing/insights#dedicated-inference).
