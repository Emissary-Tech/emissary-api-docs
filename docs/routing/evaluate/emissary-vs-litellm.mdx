---
title: 'Emissary vs LiteLLM'
description: 'How Emissary compares with LiteLLM: a router with a gateway, trained to choose the model per request, vs. an open-source gateway with config-driven load balancing and fallbacks.'
---

[LiteLLM](https://docs.litellm.ai) is an open-source SDK and proxy server that exposes many model
providers behind one OpenAI-compatible interface. Its routing features are about **reliability and
traffic management**: load balancing across deployments of the same model, retries, cooldowns, and
fallbacks to another model group when a call fails.

Emissary is also a gateway: one URL, compatible with the OpenAI and Anthropic APIs, calling
providers with your own keys. The difference is what decides *which model* serves a request. With
LiteLLM, that's rules and configuration you write. With Emissary, it's a router trained to predict
which models can do the task. See [routers and gateways](../how-routing-works/routers-and-gateways).

*Based on public information as of October 2026. Check each vendor's site for current details.*

## At a glance

| | **Emissary** | **LiteLLM** |
| --- | --- | --- |
| **Category** | Router and gateway | Gateway / proxy, with a routing layer |
| **What decides the model** | A router trained on rollouts that estimates, per model, whether it can complete the task | Rules and config you write: model groups, weights, fallbacks |
| **Per-request intelligence** | Predicts task capability from the request | Doesn't predict task difficulty on its own |
| **Cache, output-length and effort awareness** | Part of the ranking | Not part of its default routing |
| **Observability of decisions** | Per-request confidence and routing reason | Logging and cost tracking |
| **Failover, retries, load balancing** | Not covered in these docs | Core features |
| **Hosting** | Managed gateway at `api.withemissary.com` | Open source, self-hosted |

## When LiteLLM is a good fit

- You need a self-hosted gateway you control, with keys, retries, timeouts, and fallbacks under
  your own infrastructure.
- Your routing is simple enough to express as rules, or you only need reliability across
  deployments of the same model.

## When Emissary is a better fit

- You want the **choice of model** made per request from evidence about what each model can do,
  rather than hand-written rules.
- You want savings from sending easy requests to cheaper models, without maintaining routing rules
  as models and prices change.
- You want to see, per request, how confident each model was and why the router chose what it did.
